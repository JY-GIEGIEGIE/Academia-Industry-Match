# 技术转化智能匹配与产学研对接系统\-产品需求分析



## 一、产品定位定义



> **聚焦 1\~2 个垂直产业的合作撮合平台**：以科研成果库与企业需求库为双边数据基础，通过结构化标签 \+ 语义向量 \+ 大模型精排的三层匹配引擎，主动计算供需适配度并双向推荐，同时输出可解释的匹配理由、转化风险评估及合作方案建议。
> 
> 



交互方式：**双侧资料入库 → 离线匹配评分 → 双向 Top\-N 推荐 → 用户查看理由与风险 → 表达对接意向 → 平台撮合跟进**

搜索式的查询可以作为辅助入口存在，但与课题要求中的“智能推荐”不太相关，不做为主要的交互方式。

## 二、双边数据模型与来源范围



### 2\.1 科研成果侧（供给侧）

|字段类别|具体字段|数据来源|获取方式|
|---|---|---|---|
|**基础信息**|标题、摘要、关键词、作者、机构、发表/授权时间|知网/万方/国家知识产权局/arxiv|**种子数据：自动抓取**（限 2\~3 个垂直领域，总量 300\~500 条）；<br>**增量：用户手动录入**|
|**技术信息**|技术领域标签（自定义分类 \+ IPC/CPC）、技术创新点、应用场景描述、技术成熟度（TRL 1\~9）|大模型解析摘要/专利文本自动提取|**大模型自动抽取为主**，作者确认/修正为辅|
|**转化信息**|知识产权状态（已授权/申请中/已公开）、样品/中试状态、期望合作模式（转让/许可/合资/技术服务）、意向地区/行业|用户填报|**用户注册/发布时填报**|



种子数据必须真实，考虑工作量与质量，尽量聚焦。个人建议考虑选定一个主赛道，从国家知识产权局专利库 \+ 知网优秀论文中抓取 300\~500 条真实数据，作为 demo 期的"平台已有成果"。用户（科研人员）后续可手动录入自己的成果。



### 2\.2 企业需求侧（需求侧）

|字段类别|具体字段|数据来源|获取方式|
|---|---|---|---|
|**企业基础**|企业名称、所属行业、规模、地区、主营业务|用户填报|**用户注册时填报**|
|**需求信息**|技术痛点描述、期望技术方案、技术指标要求、预算范围、期望完成时间、可接受的合作模式|用户填报|**需求发布时填报**<br>（核心入口）<br>|
|**能力信息**|现有技术基础、可投入资源（资金/场地/人员）、既往产学研合作经历|用户填报|**选填**|



企业需求侧不做大规模公开数据抓取。原因在于真实的技术攻关需求很少出现在公开渠道（招股书和年报里的技术规划过于笼统，招标信息又偏向工程实施使得技术信息密度低）。个人认为应以**企业用户手动发布需求**为核心机制，平台提供结构化表单 \+ 大模型辅助润色/拆解。

## 三、更新机制

不同数据类型采取不同的策略。

|数据类型|更新策略|理由|
|---|---|---|
|**种子成果数据**<br>（抓取自专利/论文库）|**冷启动一次性导入 \+ 可配置的月度增量脚本**|课程项目不需要强实时性，月度更新足够展示动态更新能力|
|**用户自主录入的成果**|**用户自主更新 \+ 版本管理**|科研进展由用户掌握，平台提供"更新成果状态"功能（如从"实验室阶段"更新为"中试阶段"）|
|**企业需求**|**用户发布/编辑/下架，支持有效期机制**<br>**（如 90 天自动过期提醒）**|需求具有时效性，过期需求会严重伤害匹配质量|

**待明确点**：是否需要"需求到期自动邮件/站内信提醒企业更新"？推荐做，但不属于MVP范畴。

## 四、知识构建



匹配模块可检索、可计算的全部知识，构建如下三层：

```Plain Text

Layer 3: 大模型排序与解释记忆（LLM-as-Ranker & Explainer）
 - 对 Top-50 候选对，由大模型评估技术适配逻辑，并生成自然语言理由
 - 不存储为静态记忆，每次实时调用（可缓存） 
────────────────────────────────────────────────────────────
Layer 2: 向量语义记忆（Vector Memory）
 - 成果摘要、需求痛点、技术方案的文本 Embedding 
 - 存储于向量数据库（如 Milvus/pgvector），用于语义相似度召回
────────────────────────────────────────────────────────────
Layer 1: 结构化标签记忆（Structured Tag Memory）
 - 技术领域分类、TRL 等级、应用场景、行业标签、合作模式偏好
 - 存储于关系数据库（MySQL/PostgreSQL），用于硬过滤和粗筛
────────────────────────────────────────────────────────────
```



**检索与匹配流程**：

1. **硬过滤（Layer 1）**：根据技术领域标签、行业标签、合作模式兼容性做初筛（如"新能源"成果不会进入"生物医药"需求的候选集，除非用户明确勾选"跨领域"）。

2. **向量召回（Layer 2）**：对初筛后的候选集，计算成果摘要与需求痛点的语义相似度，召回 Top\-50。

3. **大模型精排（Layer 3）**：将 Top\-50 的\(成果,需求\)对及双方的完整结构化信息输入大模型，输出适配度分数（1\~100）及推荐理由。

    

**Caution: **Layer 1 的标签体系不能依赖模型自由发挥。应该人工设计一套"技术领域 × 应用场景 × TRL × 合作模式"的四维标签体系（每个维度 5\~8 个枚举值），大模型负责从非结构化文本中映射到这套预定义标签，避免随意生成标签。

## 五、匹配引擎：推荐式为主，搜索式为辅



### 主路径：双向离线评分 \+ Top\-N 推荐（推荐式）



**流程**：

1. 每当新成果/新需求入库（或存量数据变化），触发匹配pipeline：

    - 该成果 vs 全量需求库 → 计算适配度 → 为该成果生成"最匹配的需求 Top\-10"

    - 该需求 vs 全量成果库 → 计算适配度 → 为该需求生成"最匹配的成果 Top\-10"

2. 匹配分数存储于数据库的 `match_score` 表（字段：成果ID、需求ID、总分、结构化匹配分、语义匹配分、大模型评估分、推荐理由、风险评估、生成时间）

3. 用户登录首页，直接看到平台为其推荐的 Top\-N 列表

    

**理由**：

- 课题明确要求"智能匹配"和"合作智能推荐"，推荐式比搜索式更能体现主动性

- 离线评分允许大模型精排有充足时延（数秒级），避免在线实时调用的成本与延迟问题

- 可以自然展示"适配度量化打分"和"推荐理由"，直接对应课题要求

- 课程项目演示时，打开页面即看到"为您推荐"比空白搜索框更有冲击力

    

### 辅路径：响应式检索（搜索式）



保留一个搜索入口：

- 企业用户可输入"我需要固态电池电解质技术"，系统返回语义检索结果

- 科研人员可输入"寻找有钠离子电池中试能力的企业"，系统检索需求库

    

**实现方式**：直接用 Layer 2 的向量语义检索 \+ Layer 1 的筛选器，不涉及 Layer 3 的大模型精排（控制成本）。

## 六、其他问题



### 6\.1 技术成熟度（TRL）如何评估？

|方案|说明|分析|
|---|---|---|
|用户自评|发布成果时勾选 TRL 1\~9|简单但主观性强，不同人标准不一|
|大模型评估|根据摘要/描述，由 LLM 判断 TRL|推荐作为**初评**，用户可一键确认或修正|
|规则辅助|关键词规则（如"实验室合成"→TRL 3，"中试"→TRL 5）|可做，但覆盖范围有限|

**大模型初评 \+ 用户确认的思路比较理想。**在成果发布流程中，系统根据文本自动推荐 TRL 等级，用户可修改，既展示智能能力，又避免强制用户理解 TRL 概念。大模型的评估也可以参考一定的关键词规则。



### 6\.2 匹配解释做到什么程度？

|级别|内容|建议|
|---|---|---|
|L1 标签重叠|"匹配原因：同属新能源领域，均涉及固态电解质，合作模式均为技术许可"|太单薄|
|L2 结构化对比|列出双方在技术点、应用场景、合作模式、地区上的逐项对比|推荐做到这一层|
|L3 自然语言理由|"该成果在硫化物固态电解质方面的突破，正好对应贵司在动力电池安全性上的技术缺口；成果已完成中试（TRL 6），具备产业化条件，建议优先考虑技术许可模式"|**核心卖点，必须做**|



### 6\.3 反馈闭环机制（系统迭代）

推荐系统的反馈机制基本上是默认做法，需要设计轻量级反馈：

- **显式反馈**：用户对推荐结果点击"感兴趣"/"不感兴趣"

- **隐式反馈**：记录用户点击查看详情的行为

- **对接反馈**：如果用户表达了对接意向，该匹配对标记为"正样本"；如果用户明确拒绝，标记为"负样本"

    

**作为课程项目的范围限制**：不要求做复杂的在线学习，我们只数据库中**预留反馈字段**，并在界面上展示"不感兴趣"按钮。演示时可说"后续可基于反馈数据微调匹配权重"。



### 6\.4 对接流程的状态管理

推荐相当于完成了对接的起点，对接系统须管理后续流程：

```Plain Text
推荐列表 查看详情 表达意向（双向匿名） 平台初审/撮合 双方交换联系方式 洽谈中 达成合作 / 未达成
```

**MVP阶段的状态设置：**`推荐` → `已查看` → `意向已表达` → `对接中` → `已成交` / `已关闭`

每个状态变化触发站内信通知对方。体现"匹配算法 demo"和"对接系统"的区分度。



### 6\.5 技术转化风险评估的维度与输出

课题要求"技术转化风险评估"，明确评估项如下：

|风险维度|评估依据|输出形式|
|---|---|---|
|**技术风险**|技术成熟度差距（成果 TRL vs 企业要求）、技术路线兼容性|1\~5 星 \+ 一句话说明|
|**市场风险**|成果应用领域与企业主营的匹配度|1\~5 星|
|**知识产权风险**|专利状态（已授权/申请中）、权利清晰度|1\~5 星|
|**合作风险**|地理距离、合作模式偏好冲突、双方规模匹配度|1\~5 星|

**输出形式**：对每个推荐对，在详情页展示"四维风险雷达图" \+ 大模型生成的综合风险提示与规避建议。



### 6\.6 产学研合作方案推荐的内容边界

点击"生成合作方案"后，系统输出内容规划如下：

- **推荐合作模式**（技术转让 / 联合研发 / 共建实验室 / 技术咨询）

- **合作步骤建议**（接触、评估、谈判、签约、交付）

- **双方分工建议**（基于各自优势的大模型推理）

- **预期成果与里程碑**

- **风险提示与应对**

这里可以体现大模型长文本生成能力的优势，用结构化模板 \+ LLM 填充的方式实现。



### 6\.7 用户角色与权限设计

至少区分三类角色：

|角色|核心功能|看到的推荐|
|---|---|---|
|**科研人员（供给侧）**|发布/管理成果、查看推荐给自己的企业需求、表达对接意向|"这些企业可能需要您的技术"|
|**企业用户（需求侧）**|发布/管理需求、查看推荐给自己的科研成果、表达对接意向|"这些技术可能解决您的难题"|
|**平台管理员**|数据治理、用户审核、匹配质量监控、人工撮合干预|全局匹配数据看板|



### 6\.8 匿名与信息披露策略

|阶段|成果侧可见信息|需求侧可见信息|
|---|---|---|
|推荐列表|技术标题、摘要、TRL、应用领域（**隐藏机构/作者**）|企业行业、规模、需求标题、痛点概述（**隐藏企业名称**）|
|详情页|同上|同上|
|双方表达意向后|机构、联系人、完整信息|企业名称、联系人、完整信息|

理由：保护知识产权和商业机密，同时让匹配决策基于技术本身而非人情关系。



### 6\.9 聚焦

考虑到各领域评价体系、项目周期、行业模式差别大，控制数据构建的工作量与清晰度

**不试图做全领域通用平台。**

作为课程项目，我们选择 1 个核心领域 \+ 1 个辅助领域 即可。例如：

- 主赛道：新能源电池材料

- 辅赛道：新型储能技术

理由：标签体系可控、种子数据质量高、匹配逻辑可解释、答辩叙事聚焦。

## 七、MVP 功能清单与边界



### 必须做（核心）

* [ ] 用户注册/登录（区分科研/企业角色）

* [ ] 成果发布页（含大模型自动解析标签 \+ TRL 初评）

* [ ] 需求发布页（含结构化表单）

* [ ] 种子数据导入脚本（300\~500 条真实专利/论文）

* [ ] 标签体系定义与映射模块

* [ ] 向量化 pipeline（文本 → Embedding）

* [ ] 离线匹配评分引擎（三层：标签过滤 → 向量召回 → LLM 精排）

* [ ] 推荐结果页（Top\-N 列表 \+ 适配度分数 \+ 推荐理由）

* [ ] 匹配详情页（双方信息对比 \+ 四维风险评估 \+ 合作方案生成）

* [ ] 对接意向流程（表达意向 → 状态流转 → 双方信息披露）

* [ ] 管理后台（数据看板 \+ 用户/内容管理）

    

### 加分项（有时间再做）

* [ ] 搜索式检索入口（语义搜索）

* [ ] 反馈闭环（感兴趣/不感兴趣按钮）

* [ ] 需求到期提醒机制

* [ ] 简单的产业技术知识图谱可视化（成果\-技术\-需求关联）

    

### 明确不做（防范围过度扩张与其他风险）

* [ ] 全网通用领域覆盖

* [ ] 复杂的消息/IM 系统（站内信即可，不做实时聊天）

* [ ] 在线合同签署或支付

* [ ] 大规模分布式爬虫

## 十、要开的会（也作为会议纪要的材料来源）



1. **领域聚焦会**：确定到底做哪 1\~2 个垂直领域，立即开始抓种子数据。

2. **标签体系评审会**：确定 Layer 1 的结构化标签全集（这是所有后续开发的前置条件）。

3. **大模型 prompt 评审会**：统一定义"解析 prompt"、"精排 prompt"、"推荐理由生成 prompt"、"风险评估 prompt"的输入输出格式。

4. **UI 原型评审会**：确定推荐页、详情页、对接流程的交互。
