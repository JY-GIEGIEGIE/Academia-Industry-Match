## 五、使用建议

1. **先读评分细则**：每份报告的形式分（30 分）和内容分（70 分）都有明确子项，先按细则列提纲，再写内容。
2. **以定稿为基线**：项目范围、技术栈、进度、成本、风险以 `03-项目计划/G04_项目计划书_10月25日定稿` 为准；过程稿只用于追溯细节。
3. **保持编号对应**：需求规格书中的需求编号、设计报告中的模块编号、测试报告中的用例编号要能互相对应，这是终期综合评价的核对点。
4. **保留证据**：会议纪要、评审记录、测试日志、提交记录、AI 使用记录按细则要求留档；报告中的结论要能定位到证据。
5. **AI 使用说明**：细则要求说明工具、用途、人工核验责任人和核验方式；AI 生成的测试用例必须实际执行并记录真实结果。
6. **提交格式**：按细则提交可复制文字的 PDF，同时保留可编辑源文件；文件命名采用「组号_材料名称_版本.pdf」。

## 七、阅读时发现的口径差异（待团队确认）

以下差异来自对现有文档的通读，不影响文档归档，但在写需求规格书、设计报告和过程总结报告前建议统一：

1. **技术栈版本**：定稿计划书写 Python 3.11、Qwen API、BGE-M3 768 维、PostgreSQL 16；`第4章_系统开发技术方案` 过程稿写 Python 3.12、qwen3.8-flash、qwen3.7-text-embedding-flash 1024 维、PostgreSQL 17。建议以定稿为准，或在设计报告中说明最终锁定版本。
2. **成本与工时**：定稿计划书为 660 人时、1,380 元（含 15% 缓冲）；`管理与风险` 过程稿为 382 人时、276 元。两套数据差异较大，过程总结报告做计划—实际对照时需先确定基线。
3. **质量指标**：开题报告写核心接口单元测试覆盖率 ≥80%，定稿计划书写关键模块 ≥60%；建议统一为一个可验收指标。
4. **交付物清单**：课程评分细则要求四份项目文档（计划书、需求规格书、设计报告、测试报告）；定稿计划书 D1—D8 未逐一列出需求规格书、设计报告、测试报告，且 D7「项目计划书 Week 11」与细则「开题前提交」不一致。建议在计划书修订版或后续报告中补齐四份文档的提交节点。
5. **风险表**：定稿计划书风险表有可能性、影响、应对措施，但缺少触发条件和负责人；`管理与风险` 过程稿的 R1—R7 已包含触发条件和负责人，评分细则 C6 也明确要求，建议合并。
6. **匹配时延指标**：开题报告要求「匹配接口响应时间 ≤2 秒」，而定稿方案是离线匹配 pipeline；如沿用该指标，需要说明它对应的是在线查询还是离线任务。
