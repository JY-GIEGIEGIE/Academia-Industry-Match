## 五、使用建议

1. **先看评分细则**：每份报告都有明确的形式分（30 分）和内容分（70 分）条目，先按细则搭提纲再填内容。
2. **以定稿作范围基线**：范围、进度和交付物看 `03-项目计划/G04_项目计划书_10月25日定稿`；技术栈和数据口径看 `数据口径更正记录_v0.1.md` 和 `data/spec/`；过程稿只查细节。
3. **保持编号对应**：需求编号、设计模块编号与测试用例编号要前后对应，终期评审会核对这条链路。
4. **留存过程证据**：会议纪要、评审记录、测试日志、提交记录和 AI 使用记录按要求留档，报告里的结论都要能追到证据。
5. **写清 AI 使用说明**：按细则注明工具、用途、人工核验责任人和核验方式；AI 生成的测试用例必须实际跑过并填真实结果。
6. **提交格式**：按细则导出可复制文字的 PDF，同时保留可编辑源文件，文件命名用「组号_材料名称_版本.pdf」。

## 七、统一口径（2026-11-18）

以下口径已冻结，开题报告、过程稿和 PRD 中不一致的旧写法不再作为后续依据：

1. **技术栈与数据**：Python 3.11、PostgreSQL 16 + pgvector 0.8.x、BGE-M3 1024 维（备选 Qwen 1024 维）；OpenAlex 主源，不抓 CNKI/万方；需求与企业都是模拟数据。具体看 `03-项目计划/数据口径更正记录_v0.1.md`、`data/spec/data_contract_v0.1.md` 和 `data/spec/taxonomy_v0.1.md`。
2. **质量指标**：单元测试覆盖率按关键模块 ≥60% 验收，全项目不卡 80% 硬指标；检索评测按 `data/spec/eval_spec_v0.1.md` 执行：Recall@10 ≥0.70、Precision@5 ≥0.70。
3. **匹配时延**：匹配主流程是离线 pipeline，不设 2 秒在线响应指标；如果后续补了在线查询接口，再单独约定该接口时延。
4. **交付物与风险表**：课程交付物看 `05-课程要求/课程报告与评分细则.md`；后续报告补齐需求规格书、设计报告与测试报告节点，风险表按细则 C6 补齐触发条件和负责人。定稿计划书中的 D1—D8 只作历史范围参考。

- 报告定稿后同时保留「可编辑源文件 + 提交 PDF」；旧版本移入对应的 `过程稿/` 或历史目录并在 README 标明关系，不要直接删掉。
- 大型视频、答辩录屏、数据集和压缩包不要直接塞进 Git，放外部存储并在 README 记下链接和获取方式。
