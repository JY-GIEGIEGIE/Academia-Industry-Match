## 1. 目标与范围

发布动作触发真实匹配：对新发布的成果/需求与**全量异侧对象**做匹配，同一 pair 同时服务企业和科研两端，结果写入 `match_score`，P1 补 LLM 精排/理由/风险/证据。

- **B2**：标签硬过滤 + 向量余弦 + 归一化（0—100），生成规则化 `reason`，`risk`/`evidence` 暂为 `null`。
- **P1**：对 B2 结果做 LLM 精排，生成 `risk`、`evidence`、自然语言理由；失败回退 B2。
- **不修改** v0.1.2 processed 数据，不写验收库；只读 v0.1.2 标签/画像/向量，结果写开发演示库 `match_score`。

## 2. 分层与文件

| 层 | 文件 | 作用 |
| --- | --- | --- |
| B2 | `scripts/match/b2_matcher.py` | 标签硬过滤 + 向量余弦归一化，产出 `matches_b2_<version>.jsonl` |
| P1 | `scripts/match/p1_rerank.py` | LLM 生成 risk/evidence/理由，产出 `matches_p1_<version>.jsonl`，失败回退 B2 |
| 任务 | `backend/tasks.py` | Celery 任务：编排 B2→P1、幂等写 `match_score`、写 `pipeline_run` 状态 |
| App | `backend/worker.py` | `celery_app`（broker/result backend 指向 Redis） |

数据流：`v0.1.2 标签/画像/向量/需求` → B2 匹配 → P1 精排 → `match_score`（开发库）。

## 3. 数据输入（v0.1.2）

| 文件 | 内容 | 用途 |
| --- | --- | --- |
| `achievements_labeled_v0.1.2.jsonl` | 成果标签、TRL、IP、指标 | primary `tech_field`、TRL |
| `demands_v0.1.2.jsonl` | 需求 `tech_fields`、`required_trl` 等 | 硬过滤目标字段、上下文 |
| `capability_profiles_v0.1.2.jsonl` | 成果中文画像 | P1 上下文（机器画像，非唯一证据） |
| `embeddings_v0.1.2.jsonl` | 成果/需求 1024 维向量 | 余弦相似度 |

需求侧向量 `object_type=demand`、`text_type=need_profile`；成果侧 `object_type=achievement`、`text_type=capability_profile`。

## 4. B2 匹配

1. **严格硬过滤**：成果的 primary `tech_field` 必须命中需求 `tech_fields`，否则直接 `pass`（不进结果）。
2. **算分**：`cosine(demand_vector, achievement_vector)` → `normalize_cosine`（`max(0, min(1, cos)) * 100`）→ 0—100。
3. **固定 ID**：`match_id = match_{demand_id}_{achievement_id}`，同一 pair 两端唯一，避免双向分数不一致。
4. **规则化 reason**：`技术领域匹配（{code}）；语义相似度 {score}/100；成果 TRL {x} 与需求 TRL {y} 对比`。
5. **risk / evidence 置 `null`**（B2 未精排，见 API 契约 §6.4 的 null 语义）。

得分口径：`total_score = semantic_score = 归一化余弦`；`tag_score = 100`（硬过滤通过的二元门）；`llm_score = null`。

## 5. P1 精排

对 B2 结果逐条调 `llm_client.chat_json`（`qwen3.8-flash`），要求输出：

- **reason**：自然语言推荐理由（100 字内）。
- **risk**：四维 `technical / market / ip / collaboration`，每维 `{score(1—5), description}`，加 `overall {summary, mitigation[]}`。风险依据只来自给定字段，论文 `ip_status` 默认 `unknown`、不得推断为已授权。
- **evidence**：`tag_matches`（命中标签）、`snippets`（原文摘录）、`metric_matches`（指标对比）。机器画像只能帮助理解，不作 snippet 来源。
- **source_ref allowlist**：`achievement.title_original`、`achievement.abstract_original`、`demand.title`、`demand.pain_point`、`demand.expected_solution`；`achievement.abstract` / `achievement.title` 作为别名归一化；`achievement.profile` / `key_metrics` 等不合法。
- **证据校验**：snippet 必须是 source_ref 对应字段的逐字子串，不能带省略号；超过 200 字保留原文前缀；risk 四维/overall 必须完整；reason 超过 100 字截断；任一项不合法就回退 B2。

**写死回退**：`try-except` 包裹，API 报错/超时/输出非法 → 保留 B2 结果（`risk`/`evidence` 仍为 `null`、`reason` 仍为 B2 规则理由），不中断任务。缺上下文（demand/label 找不到）同样原样保留 B2。

## 6. 匹配结果字段（match_score）

| 字段 | 说明 |
| --- | --- |
| `match_id` | `match_{demand_id}_{achievement_id}`（主键） |
| `total_score` / `tag_score` / `semantic_score` | 0—100；B2 阶段 `total=semantic`，`tag=100` |
| `llm_score` | 精排分，本轮暂 `null` |
| `reason` | B2 为规则化理由，P1 成功后为自然语言理由 |
| `risk` / `evidence` | B2 为 `null`；P1 成功后按 §5 结构填充 |
| `model` / `prompt_version` | B2 为 `b2` / `b2-rule-v1`；P1 成功后为真实精排模型/Prompt 版本 |
| `dataset_version` / `taxonomy_version` / `embedding_model_version` | `v0.1.2` / `v0.1` / `qwen3.7-text-embedding-flash-1024-v1` |
| `is_stale` | 数据/模型变更后标记失效，当前 `false` |

## 7. Celery 任务与幂等

- **App**：`backend.worker:celery_app`；broker `redis://127.0.0.1:6379/0`，result backend `redis://127.0.0.1:6379/1`。
- **任务**：`run_match_for_achievement(achievement_id, run_id, version)` / `run_match_for_demand(demand_id, run_id, version)`。
- **幂等**：任务先连开发库（`DATABASE_URL`，必须指向 `s2_mvp_*`）`SELECT match_id FROM match_score WHERE match_id = ANY(%s)`；已存在的结果跳过插入，**只对新增候选做 P1**，避免重复 LLM 调用；插入再叠加 `ON CONFLICT (match_id) DO NOTHING` 兜底。
- **Top-K**：P1 只对新增候选按分数排序后的 Top-K（默认 10，`P1_TOP_K` 可调）调用 LLM，其余保留 B2。
- **未知对象**：需求/成果不在 v0.1.2 静态输入或缺向量时抛 `MatchObjectNotFound`，状态写 `failed`，不再 success 0。
- **状态**：任务启动写 `pipeline_run.status='running'`，结束写 `success`（P1 全成功）或 `partial`（P1 失败回退 B2）；B2 异常 → `failed` 并抛出；`input_count` 写本次 B2 候选数。

## 8. 任务状态（pipeline_run，stage=match）

| 状态 | 含义 |
| --- | --- |
| `running` | 任务执行中 |
| `success` | B2 + P1 全部完成 |
| `partial` | B2 完成、P1 至少一条失败回退 |
| `failed` | B2 抛异常 |

沿用现有 `pipeline_run` 表（`stage='match'`），不新建任务表；`finished_at` 在 running 时为 `NULL`。

## 9. 运行方式

```bash
# 离线脚本（可选，产出中间文件，便于 20 条样例给 S-11/S-14 解阻塞）
python scripts/match/b2_matcher.py --version v0.1.2            # 全部或 --top-k 10
# 每需求 Top-1（跨需求样例）；演示 pair 用 --match-ids 显式纳入
python scripts/match/p1_rerank.py --version v0.1.2 --per-demand 1 --limit 20
python scripts/match/p1_rerank.py --version v0.1.2 --match-ids "match_dem_005_ach_openalex_W4200428349"

# Celery（发布 API 就绪后由 S-11 触发）
celery -A backend.worker worker --loglevel=info
celery -A backend.worker call backend.tasks.run_match_for_demand --kwargs='{"demand_id": "dem_001"}'
```

## 10. 依赖与约束

1. **迁移 0003**：`match_score.risk/evidence` 可空——B2 阶段二者为 `NULL`；`model/prompt_version` 仍必填，B2 写 `b2` / `b2-rule-v1`。须先应用 S-12 交接包中的 `0003_publish_match.sql`（并补双端 Top-K 索引）。
2. **数据库**：`DATABASE_URL` 指向开发演示库 `s2_mvp_20261125`（S-12 在 docker-compose 里设置）；不写验收库。
3. **环境**：Python 3.11 + Celery + Redis + psycopg 3；`qwen3.8-flash` + `qwen3.7-text-embedding-flash`（1024）。
4. **不修改** v0.1.2 processed 数据；本轮发布只允许绑定现有记录，不允许改技术文本或新建 ID；改文本/新建需先接入重新抽取与向量化，当前会报错而不是静默成功 0。

## 11. 验收口径（对齐 S-10 完成标准）

- 发布后能创建匹配任务并产出真实 `match_score`；同一 pair 唯一。
- 企业端/科研端查询同一 pair 得到同一 `match_id` 与分数。
- B2 的 `risk`/`evidence` 为 `null`；P1 精排失败可回退。
- 任务重复执行不产生重复行；状态可查询。
- 不修改 v0.1.2 数据；不写验收库。
