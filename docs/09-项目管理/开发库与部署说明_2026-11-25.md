## 3. 建开发库

```bash
# 创建 s2_mvp_20261125，并全量导入 v0.1.2（含 0001—0004 迁移）
./.venv/Scripts/python.exe scripts/dev/create_dev_db.py \
  --zip "D:/path/to/S-08_v0.1.2_2026-11-23.zip"

# 重建（会删库，仅限开发库；带上包以校验整包哈希）
./.venv/Scripts/python.exe scripts/dev/create_dev_db.py --recreate \
  --zip "D:/path/to/S-08_v0.1.2_2026-11-23.zip"

# 只建空库，不导入
./.venv/Scripts/python.exe scripts/dev/create_dev_db.py --skip-load
```

脚本做的事：从 `.env` 的 `DATABASE_URL` 派生同名主机/账号；创建 `s2_mvp_20261125`；用
`load_db.py --dataset-version v0.1.2` 显式传入六个 processed 文件、两个 eval 文件和
`data/manifests/private_data_v0.1.2.json`；运行时报告写到
`data/manifests/load_report_v0.1.2_dev.md` / `import_v0.1.2_dev.json`（不入库）。

建库前脚本会先校验 manifest 里的 8 个文件哈希（6 processed + 2 eval）；传 `--zip` 时再校验整包哈希，校验失败直接退出，不会先建空库。不带 `--zip` 时只做文件级校验。

> 注意：`load_db.py` 的默认路径解析只区分 `v0.1-thin` 和 `v0.1`，所以这里必须显式传
> `--achievements/--labeled/...`，不能只写 `--dataset-version v0.1.2`。
>
> `private_data_v0.1.2.json` 已登记 `package.sha256`（`0ff57082…5904a`），因此 `--zip`
> 会同时校验整包与 6 个 processed 文件；包哈希的本地记录在
> `data/manifests/S-08_v0.1.2_2026-11-23.zip.sha256`，包内 `SHA256SUMS.txt` 也可单独核对。

## 6. 迁移内容

### `0003_publish_match.sql`

- `match_score.risk` / `evidence` 改为可空：B2 先出分数与规则理由，P1 再补风险/证据。
- 新增 `(demand_id, total_score DESC)` 与 `(achievement_id, total_score DESC)` 复合索引，服务双端 Top-K。
- 幂等：每次 `--migrate` 重跑安全。

### `0004_users_publish_intent.sql`

- `app_user`：`user_id`、`username`（唯一）、`password_hash`、`role`（researcher/enterprise）、`display_name`、`created_at`。
- `achievement` / `demand`：`publisher_user_id`（FK，删除账号置 NULL）、`published_at`，附发布者索引。
- `intent`：`intent_id`、`achievement_id`、`demand_id`、`initiator_user_id`、`status`（expressed/confirmed/declined/closed）、`contact_revealed`、`created_at`、`updated_at`。
- 设计口径：**一个 (achievement, demand) pair 只有一条意向**，`initiator_user_id` 记录发起方；另一方确认后置 `confirmed`。`contact_revealed` 与 `confirmed` 的一致性由 API 保证（同一条 UPDATE 写入），数据库不加强制 CHECK，避免 closed 等后续状态被误伤。
- 现有 v0.1.2 记录的发布者字段保持 NULL；只有发布动作才写入。
