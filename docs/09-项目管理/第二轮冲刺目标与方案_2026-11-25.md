## 1. 一句话目标

做出一个**可演示的完整业务闭环**：科研用户登录后发布一项成果，企业用户登录后发布一条需求；发布动作写入真实数据库并触发匹配引擎；双方在各自入口看到对方并完成真实匹配；随后表达意向、双方确认，最后以 mock 联系方式展示“披露完成”。

不是“前端拿两条假数据演一下”，而是：**发布走真实 API、数据入真实库、匹配走真实引擎、意向状态真实持久化**。只有最后的联系方式内容允许 mock。

## 3. 演示闭环

1. **科研用户** `research_demo` 登录，从 v0.1.2 数据池选择一项成果，通过成果发布页确认发布。
2. **企业用户** `enterprise_demo` 登录，从 v0.1.2 数据池选择一条需求，通过需求发布页确认发布。
3. 发布后创建真实 `pipeline_run` / Celery 匹配任务，对新成果、新需求执行匹配；结果写入 `match_score`。
4. 企业端看到该成果，科研端看到该需求；同一 pair 从两侧进入同一详情，分数/理由/证据一致。
5. 任一方点击“表达意向”；另一方登录后确认；双方确认后，页面展示 mock 联系方式，标记“演示披露”。
6. 详情页展示适配度、推荐理由、标签/摘要证据、四维风险；LLM 失败时显示“待精排/评估”，不编造。

## 4. 技术方案

### 4.1 技术栈对齐

| 层 | 本轮采用 | 与原计划关系 |
| --- | --- | --- |
| 前端 | Vue 3 + TypeScript + Vite；新增登录/发布页使用 Element Plus | 与原计划一致；现有推荐/详情页保留已验收组件 |
| 后端 | Python 3.11 + FastAPI + Pydantic 2 + **SQLAlchemy 2.0** | 与原计划一致 |
| 异步任务 | **Celery + Redis**，匹配任务持久化、可重试 | 与原计划一致 |
| 数据库 | PostgreSQL 16 + pgvector 0.8.x | 与最终项目计划一致；数据侧已冻结 |
| 模型 | qwen3.8-flash + qwen3.7-text-embedding-flash 1024 | 与数据侧一致 |
| 部署 | Docker Compose + **Nginx**（静态前端 + API 反代） | 与原计划一致 |
| 可视化 | 风险雷达已有等效组件；ECharts 仅在需要重做时引入 | 保留已验收 UI，避免无业务收益重写 |

说明：现有前端是已验收的自定义组件，不在本轮为了“库一致”整体重写；新增登录/发布页按 Element Plus 实现，推荐/详情页沿用现有视觉。ECharts 不是业务门槛，风险雷达已有可用的等效展示。

### 4.2 数据模型增量

在开发演示库中新增/扩展：

- `app_user`：`user_id`、`username`、`password_hash`、`role`（`researcher`/`enterprise`）、`display_name`、`created_at`。
- `achievement.publisher_user_id`、`demand.publisher_user_id`：发布者归属；现有数据为 `NULL`。
- `achievement.published_at` / `demand.published_at`：发布时间。
- `intent`：`intent_id`、`achievement_id`、`demand_id`、`initiator_user_id`、`status`（`expressed`/`confirmed`/`declined`/`closed`）、`contact_revealed`、`created_at`、`updated_at`。
- `match_score.risk` / `evidence` 允许 `NULL`（B2 未精排时）。
- Celery 任务使用现有 `pipeline_run`（`stage=match`）记录状态；不新建第二套任务表。

### 4.3 发布与匹配

- 成果发布页：从 v0.1.2 数据池选择一项成果并预填，用户确认；本轮不允许修改技术文本或新建 ID，发布只绑定现有记录。提交后写入真实 `achievement` 并设置 `publisher_user_id`、`published_at`，复用已有标签/画像/向量。
- 需求发布页：从 v0.1.2 数据池选择一条需求并预填，用户确认；本轮不允许修改技术文本或新建 ID。提交后写入真实 `demand` 并设置发布者，标签/场景/合作模式沿用已有记录。
- 发布成功后创建 `pipeline_run(stage=match)`，Celery 任务对该对象与全量异侧对象做 B2 匹配；Top-K 做 LLM 精排/理由/风险/证据。
- 匹配结果写入 `match_score`；前端轮询匹配状态，完成后刷新推荐。
- 同一 pair 只写一条记录，`match_id = match_{demand_id}_{achievement_id}`；两端共用，避免双向分数不一致。
- 不允许前端写死匹配结果；演示必须由发布触发真实任务。

### 4.4 认证与角色

- 只做**演示账号登录**，不做注册、找回密码、复杂权限：
  - `research_demo` / `enterprise_demo`，密码由 S-12 初始化脚本写入（哈希存储）。
  - 登录返回短期 token；后端校验发布者/意向发起者身份。
- 管理后台、管理员角色不在本轮。
- 页面明确标注“课程演示账号，非真实用户体系”。

### 4.5 意向与联系方式

- 意向状态：`expressed`（已表达）→ `confirmed`（双方确认）；`contact_revealed` 是独立布尔标记，表示双方确认后的演示披露。
- 双方都可发起；对方确认后，状态才变为 confirmed，并置 `contact_revealed=true`；任一方拒绝则 `declined`。
- 联系方式不存真实信息；确认后 API 返回固定的 mock 联系方式（如 `demo-contact@example.com` / `138****0000`），页面标注“演示联系方式”。
- 联系披露只做界面与状态效果，不做真实短信、邮件、IM。

### 4.6 API 契约扩展

在现有 API 契约基础上新增：

- `POST /api/v1/auth/login`、`GET /api/v1/auth/me`
- `POST /api/v1/achievements`（发布成果）
- `POST /api/v1/demands`（发布需求）
- `GET /api/v1/pipeline-runs/{run_id}`（匹配任务状态）
- `POST /api/v1/intents`、`POST /api/v1/intents/{id}/confirm`、`GET /api/v1/intents`
- `GET /api/v1/intents/{id}/contact`（双方确认后返回 mock 联系方式）

原有成果/需求/匹配读接口保持不变；契约变更由 S-11 更新文档和测试。

### 4.7 训练实验（S-16，PM 主责）

- 目标：用弱监督方式训练轻量 reranker，验证“小模型能否在冻结的人工测试集上改善匹配排序”，作为本轮技术亮点。
- 特征：标签重叠、primary tech、场景/合作模式、TRL 差距、向量相似度、年份/引用等。
- 训练集：LLM/规则弱标签与构造 pair；**50 对人工 pair 只做冻结测试集，不参与训练**。
- 对比：B2、弱监督 reranker、LLM 精排；指标为 nDCG@10、pair 准确率/AUC。
- 结果可以是正增益，也可以是负结果；负结果同样作为实验结论保留，不阻塞主链。
- 不做 LLM fine-tune、embedding fine-tune、端到端双塔；模型文件不入库，只保留脚本、配置和报告。
- 若训练结果明确正向，可作为 API 的可选 reranker；若没有提升，不接入线上路径。

## 6. 验收标准

### 主链（P0 + P1）

- `research_demo` 登录后能发布一项成果；`enterprise_demo` 登录后能发布一条需求。
- 发布写入真实数据库，`publisher_user_id` 正确；不是前端本地数据。
- 发布触发 Celery 匹配任务；任务状态可查询；匹配结果写入 `match_score`。
- 企业端能看到该成果，科研端能看到该需求；同一 pair 两端 `match_id`/详情一致。
- 意向可发起；对方可确认；双方确认后显示 mock 联系方式；未确认不显示。
- 刷新页面/重启服务后状态仍存在。
- 不修改 v0.1.2 processed 数据；验收库不写入。

### P1 质量

- LLM 精排/理由/风险/证据在演示 pair 上可展示；失败回退 B2 并显示“待精排/评估”。
- Nginx 静态前端 + API 反代可用；Docker Compose 一键启动。
- 后端测试、前端 build/test/lint、端到端脚本通过。
- 三条演示：科研发布、企业发布、意向确认/联系方式 mock；至少一条同一 pair 两端互看。
